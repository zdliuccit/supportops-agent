# 发布、回滚与故障处理 Runbook

适用实现：2026-10-15 当前工作区，单 API、共享 Worker、PostgreSQL、Redis 和 Web 管理台；迁移源截至 `20261015_0046`。本文提供处理流程，本轮未执行发布、迁移、故障演练、备份恢复或验收。[应用模板](../../../deploy/runtime/README.md) 已提供锁文件构建/运行、单执行者迁移、同源 SSE 和外层 TLS 示例。真实工单连接器、企业秘密 provider、完整部署前校验/smoke、容量 SLO、RTO/RPO 和擦除策略仍待各自任务，不据此宣称具备生产上线条件。

## 处理角色与事实

| 角色 | 职责与权限边界 |
| --- | --- |
| 发布维护者 | 核对版本/迁移兼容、安排停机与恢复；部署环境和变更窗口须明确授权 |
| 基础设施负责人 | 检查数据库、Redis、进程存活、时钟、存储及隔离备份；不手工覆盖 Run/动作事实 |
| 租户平台管理员 | 查询本租户 Trace、attempt、通知、告警和凭据审计；按版本执行受控死信/尝试处理 |
| 知识负责人 | 核对已发布版本、ACL、有效期和关键词索引事件；修复来源或审核后重新发布 |
| 支持处理人员 | 在显式 Mock 项目范围内处理工单；读取上下文还需独立权限和知识 ACL |
| 安全负责人 | 确定受影响主体、凭据修订、工具/知识版本及隔离/恢复范围，保留最小必要审计 |

排查记录只包含租户内资源 ID、Run/attempt/action/receipt、correlation ID、时间、错误码、generation、版本和处理结果。日志、截图、工单备注不复制密钥、连接串、原始 Prompt、用户正文、隐藏推理或完整外部响应。告警只是采样，数据库业务回执及追加审计是判断依据；确认已阅只记录看到告警。

## 发布前与发布顺序

1. 固定拟发布代码、`uv.lock`、`pnpm-lock.yaml`、配置变更和数据库当前 Alembic revision，核对 API/Web 契约及新增字段。记录哪些迁移尚未执行、哪些测试仍暂缓；测试暂缓期间不得写“生产验收通过”。

新 Agent 发布清单同时记录 manifest digest、Prompt/图/源码/依赖/模型/工具 Schema/目录/授权/审批/检索策略摘要。版本历史的“发布清单”可与活动版本比较，发布维护者须记录两个固定版本 ID，不把“无已知差异”当作通过评测：未知/legacy_unrecorded 不补造，integrity_failed 隐藏清单并拒绝激活。evaluation保持发布时not_assessed，最新评测及当前门禁另查：staging/production须具备匹配固定版本/当前范围/批准集和负载的最新实测结果，缺失/过期/失败拒绝；local/dev/test仅开发激活仍标未验收，模型连通测试不替代业务验收。当前W19执行器/实测仍待，灰度默认无批准策略，不能启动。清单不冻结知识语料、不赋予运行许可，实际知识与凭据分别在检索/Run 创建时绑定。
2. 在获授权的隔离环境先准备业务库与 checkpoint schema 的一致性备份，并验证恢复流程。保留对应密封 provider/主密钥的受控恢复引用；缺主密钥的密文备份不保证可用。实际备份策略与 RTO/RPO 在 W22.6/W22.7 单独交付。
3. 确认目标环境、域名和秘密注入。production 禁止 Mock、开发默认秘密、私网模型端点和非 PostgreSQL 数据库，并需显式模型允许列表；本地 `.env.example` 不能直接充当生产配置。批准负载与外部接入契约未就绪时，仅使用隔离开发环境。
4. 安排 API 入口停止接收新请求，停止旧 API/旧 Worker 和独立模型探测者，记录在途 Run/动作。Worker 收到退出信号后停止新领取，默认等待 30 秒，超时取消后再等待最多 15 秒；`shutdown_incomplete` 需继续确认旧进程是否存活，不能据此直接重放副作用。升级 0028 前特别停止旧 API BackgroundTasks 探测者；升级 attempt 治理前确认旧 Worker 不再写 checkpoint/外部目标。
5. 由单个迁移执行者在指定环境执行批准的 Alembic 升级。应用模板 migrate.py 以 PostgreSQL 会话 advisory lock 串行完整业务迁移及 checkpoint 初始化；所有执行者使用同一入口，旧直接 Alembic 命令不自动受锁约束。要求现有库至少在 0017 已知基线，空库/更早版本另行审核（0005 含清空历史操作）。先升级 schema，再启动匹配的 API/Worker/Web；不得用应用自动建表替代迁移。0018–0046 的所有未执行迁移均按链顺序处理，0040 后旧 JWT 重新登录；0041 清单不等于业务评测通过且历史不补造。
6. API/Worker 使用同一份 schema、队列名、租约/预算、秘密 provider 和特性开关；启动顺序先数据库/Redis、迁移，再 API/Worker，最后开放 Web/入口。API 启动可能按配置 bootstrap 初始身份，已有环境应明确 bootstrap 设置，不能创建未经批准的管理员。
7. 在用户恢复验收后，按批准范围检查 live/ready、登录、管理员隔离、固定版本会话、SSE 重连、Worker 心跳与执行、关键词 ACL、Mock 审批/对账。Web 与 API 同步上线，尤其知识版本分页、审批/动作等待和新响应字段不能只升级一侧。
8. 开放入口后查看真实租约、排队/有效执行/等待、死信、模型调用账本、回执和缺失指标。没有快照时允许 unknown，等待 Worker 首次协调；若出现跨租户、权限绕过、秘密暴露或未知副作用，停止继续扩大范围，按下文处理。

## 非破坏性回滚

Agent配置回滚使用版本历史“检查并激活”：目标旧版本仍须满足当前环境门禁；退出版本写入withdrawn_at/by和追加审计，不能解除或直接重新激活，修复需新候选。原会话不改版本，尚未发出的审批/动作停止新写许可并由维护流程失效；执行中或未知结果继续只读复核/有限对账。隔离Mock目标事务与撤回锁串行，回滚前已提交的副作用保留真实回执，不当作已撤销；真实系统另按目标契约处理。0042评测历史/0043撤回事实的降级遇到历史会拒绝，不启动绕过新门禁或新写冻结的旧API/Worker。

1. 停止新请求/新派发，记录当前发布版本、schema revision、在途 attempt、审批消费和未知动作，等待或隔离旧执行者。先控制新增影响，不删除历史。
2. 区分应用缺陷、配置缺陷、schema 不兼容和外部结果未知。若旧应用能兼容已扩展 schema 和历史状态，使用经批准的旧代码与匹配 Web/配置恢复；否则保持隔离，修复前向兼容版本。不得在新 schema 上盲目启动不了解 waiting 状态、fencing 或撤销语义的旧 Worker。
3. 保留数据库扩展字段、版本、Run、attempt、审批决定/消费、动作幂等键、回执、告警和登录会话。0037 的撤销不能“回滚”为可用；0038 多来源升级包、0039 告警、0040 登录会话历史的降级会拒绝，不能清空历史或启动绕过会话校验的旧 API 来绕过。
4. 配置回退不能把旧 Run 指向新模型/凭据，不能改变冻结参数或审批主体，也不能清零恢复/对账次数。预算缺口须通过新获准上下文解决。
5. 未知动作继续查询目标事实与对账；只有证明未执行且满足现行权限/策略及未撤回版本写许可时，才能沿原逻辑动作键继续；被撤回来源不能借新Run换执行上下文重发。备份恢复不是消除未知副作用的方法，恢复后开放访问前还需删除/隔离标记重施及动作对账，相关实现仍待 W21/W22.7。
6. 恢复后比较版本、有效许可、实际回执和追加审计，记录恢复范围及未解决项。远程回滚、数据库降级或数据恢复由明确授权的维护者执行。

## API、Worker 与通知故障

| 信号 | 排查与处理 | 关闭条件 |
| --- | --- | --- |
| `/health/live` 不可用 | 检查 API 进程与启动配置，不先归因于模型；不输出配置中的秘密 | 进程恢复且对应就绪检查可用 |
| `/health/ready` 503 | 响应仅区分 PostgreSQL/Redis unavailable；检查相应依赖与连接权限，保留 DB 业务事实 | 必需依赖恢复；ready 不代表模型、schema 或业务链路验收通过 |
| Worker 服务租约过期 | 检查进程、独立心跳、时钟和维护失败；服务租约默认 15 秒，心跳 5 秒 | 新的有效共享服务租约；不据此判定所有旧 Run 已结束 |
| 健康快照缺失/stale | 状态 GET 不重算；检查 Worker health 任务。默认 computed/observed 任一超过 90 秒或超前 5 秒为 stale，调整刷新周期时同步评估阈值 | 协调任务生成可信时间和解释，不手工写 healthy |
| Redis 通知丢失/积压 | 对比持久化 queued Run、通知状态和 Redis 深度；深度可能含重复通知，不代表实际执行数 | 数据库通知按原 Run 被领取/终态处理，重复通知不产生新业务 |
| 通知 `dead_letter` | 租户管理员先 `GET /v1/admin/run-notifications?status=dead_letter&page=1&page_size=20`；修复原因后用当前 `expected_revision` 调用 `POST /v1/admin/run-notifications/{id}/retry` | 原 queued Run 获得有限新投递窗口；`delivered` 只表示 Redis 接受，继续追踪领取 |
| Run attempt 租约过期 | `GET /v1/admin/runs/{id}/attempts` 与 Trace，核对当前 generation、owner、租约、恢复次数和副作用；默认只读且证明无副作用才自动恢复，最多 2 次 | 新有效 attempt 或明确 cancelled/failed；旧许可不能提交 |
| 旧 Run 无可信 owner | 先实际确认旧进程停止；管理员 `POST /v1/admin/runs/{id}/recover` 携当前 `expected_generation` 与确认/取消选择。有效租约、终态、取消中和未知副作用不强制移交 | 服务端受控恢复/取消及追加事件，无新 Run/输入重复 |

版本冲突返回 409 时重新读取，不机械重试写请求。数据库直接更新 status/generation、删除通知、向 Redis 批量注入新 Run 或扩大恢复上限均不能代替受控处理。

## 模型、预算、检索与工具故障

| 场景 | 处理步骤 |
| --- | --- |
| 模型 429/超时/端点故障 | 查询当前租户错误事件、固定模型版本、模型调用账本及能力探测状态；识别容量/配额/路由/故障来源。保留已有失败或未知消费；不得给旧 Run 换最新端点/密钥、扩大重试或把缺 usage 当零。新配置需能力验证、发布和明确激活，新会话按固定版本使用 |
| 模型凭据不可用/撤销 | 查看凭据修订及脱敏访问审计。先修复被批准的 provider/身份，不静默降级；旧 revision 永久撤销时停止该引用的后续调用/提交。轮换只产生新 revision，不解除撤销；已出站请求不保证撤回 |
| 预算/额度耗尽 | 查看 Run budget 和调用账本，累计消费不能恢复清零。若获准 Mock 升级来源已保存，可查看升级包；失败 Run 不继续写动作，需新的有效授权完成确认。不要用反复新 Run 绕过同一问题/逻辑动作去重 |
| 首输出慢/观测缺失 | 以 SDK 首个非空输出块阈值判定；阈值默认未设置。模型/工具/API/客户端时间不跨时钟相减。completed 超过 60 秒宽限后检查缺失模型字段；无模型调用不要求模型指标，客户端未上报不能证明链路失败 |
| 关键词检索无结果 | 先核对当前租户、用户和知识版本 ACL、发布/有效期、查询范围、关键词策略与预算；无证据回答需保留未确认/追问/升级，不开启向量功能或放宽 ACL 作为修复 |
| 索引失败/死信 | 管理员读取文档 `/index` 和 `/v1/admin/knowledge/index-jobs` 元数据，修复版本/Worker/依赖后调用文档 `/index/rebuild` 或任务 `/{id}/retry`（当前 `expected_attempts`）。保留旧死信和替代事件关系，有限重试，不复制失效正文到新索引绕过治理 |
| 工具拒绝/撤销/Schema 不符 | 读取 Run security-events、固定实现/目录版本和当前 grant，核对资源参数与启停。拒绝不等于系统故障；修改必须经控制面审计，不改 Prompt、删除门禁或把高风险定义降级以继续执行 |
| 维护观测失败 | 检查 `worker_periodic_failed` 稳定任务名和缺失/stale；只恢复对应维护任务。观测失败不覆盖已提交 Run/动作状态，告警为空或已阅都不作为恢复证明 |

## 灰度控制与巡检失效

工具数据错误定位：TOOL_RESULT_INVALID/TOOL_OUTPUT_SCHEMA_UNSUPPORTED先检查固定输出Schema与工具实现，不透传任意字段或截断JSON来绕过；TOOL_CONTEXT_AUTHORIZATION_CHANGED检查已用调用ID/摘要、当前目录/角色/Mock开关、工单权限/版本与五分钟观察期限，接收时间不能延长寿命。TOOL_SOURCE_CONFLICT保留同请求公共白名单标量冲突和未完成标记，交人工复核或补充证据；不选择一方作为已确认根因。已用来源不能通过清除ContextSnapshot、裁剪或重试清零解除复检。需要重新观察时提交新轮次，原来源/Run事实保留；当前测试/性能验收未执行。

补偿意向处理：0046提供本人动作的compensation-readiness/compensation-proposals；unknown/submitted无独立目标先对账，不通过新业务键重做或人工填成功。当前独立回执能定位未关闭Mock工单时，允许本人显式保存关闭意向，固定源回执/目标版本/授权摘要、最低R3/R4。提案不继承原批准，GET变化/不适用保留历史；当前无批准/排队/执行器，不调用客服close绕过。未来实际补偿必须独立新动作/非本人审批、重新授权和目标/接管复检；不把保存proposed或HTTP201当作已关闭，0046及验收未执行。

1. 在历史版本“灰度发布”保存固定基线/更新候选/主体和数值策略草稿，记录rollout ID、policy/definition digest。由受控配置批准 `SUPPORTOPS_RELEASE_ROLLOUT_POLICY_DIGEST`，配置批准只批准门槛，不产生评测结果。两版本都须有当前完整passed实测，当前W19未接通不能启动；开发豁免也不能启动灰度。
2. 默认巡检30秒、每批10个，过期90秒；过期阈值必须大于两倍周期。规模扩大需确认轮转容量，超出时安全关闭候选新流量，不假定每个灰度固定30秒都被扫描。Worker维护失败使用既有degraded观测，修复后仍需检查实际灰度状态；active仅巡检过期时可随成功巡检恢复有效性，已经paused必须人工显式恢复。
3. 新会话稳定分组；初始≤10%，每次扩大≤10个百分点，最高90%保留基线组。每次启动/恢复/扩大都开启新观察轮次，旧轮次不充数。观察期至少300秒，两组足量终态样本、无等待/取消、完整费用/延迟、结果绑定及绝对/相对门槛通过后才能人工扩大。缺失不填零、超5000不截断放行；期满缺失或已知失败由系统暂停，低流量需重新批准合适窗口，不临时降低安全要求。
4. 使用详情的基线/候选门禁、观测checks、巡检时间和固定原因码定位；只读元数据不证明业务解决或客户端SLO，客户端上报不能批准扩量。审计分页显示真实人工/系统、修订/轮次/比例，冲突409后刷新同一记录再决定，不自动重放控制命令。
5. 暂停只停止新增候选会话。停止不可复活，并永久撤回曾启动候选的新激活/新写动作；旧会话、已发出/未知动作、审批和回执保留且继续当前授权下的只读对账。全量须另经“检查并激活”，同事务关闭灰度；提升候选不撤回它，激活其他版本则撤回已启动候选。修复撤回版本需发布新候选，不手工清除withdrawn字段。
6. 0044未执行；包含灰度历史的降级会拒绝，不通过旧API/Worker重写会话选版或绕过撤回。没有实际启用、故障演练、浏览器验收或负载实测。

## 审批与动作处理步骤

1. 先读取动作、`/v1/actions/{id}/receipts`、关联审批和本 Run 阶段/安全事件，区分 proposed、等待、queued、执行、unknown、needs_attention 和 verified 回执。
2. 审批绑定固定动作参数、版本、期限和非本人范围；等待已释放模型 Worker。拒绝、过期、撤权和改参不能手工更改为批准；改参使用新提案/新审批，保留旧决定。平台管理员角色不自动具备 Mock 业务权限。
3. 动作超时或丢响应保留 unknown，先查询最终目标状态。获准原主体可用 `POST /v1/actions/{id}/reconcile` 提交当前 generation/reconciliation_count 与有效上下文，服务端复检权限及次数；默认自动最多 6 次、人工扩展有限累计最多 10 次。收到 202 仅表示请求已入队。
4. 对账 conflict、额度耗尽或目标不能证明结果时交支持人员处理。不得重复 `/execute`、改幂等键、新建相同动作或清理回执来制造成功；HTTP 200/submitted 也不是 verified。
5. Mock 客服认领、备注、回复、关闭、升级和释放使用显式 `ticket_handle` 项目权限及当前版本/同键同参数命令；接管冻结同问题/来源会话的 Agent 写动作。上下文读取还需 `support_context_read`，原主体来源权限和双方知识 ACL 独立复检。
6. 当前只支持隔离 Mock 的目标隔离/独立查询，不能把关闭迟到 Mock 请求的实现当作真实外部 API 保证。真实目标由 W17.8–W17.10/W20 接入前保持停用。

## 数据或凭据泄露响应

1. 记录最小证据和受影响范围，限定租户/用户、凭据 revision、Agent/模型/知识/工具版本、时间、correlation/Run/动作/回执标识；避免在处理记录中再次复制泄露内容。
2. 由获授权负责人停止相关入口/Agent/工具、新调用或外部目标权限，隔离可能仍存活的执行者。模型凭据通过对应管理员 revision 撤销接口永久撤销并保留理由摘要/审计；若涉及目标系统凭据，由该系统负责人执行其自身撤销，不能假定本地撤销会撤回已发请求。
3. 检查固定引用、原主体/客服权限、知识 ACL、工具门禁和外部响应。使用最小元数据审计核对后续拒绝；Trace/告警的脱敏不能代替对原始存储、外部副本与已发调用的调查。
4. 旧 revision 不解除撤销；新凭据与新版本经独立验证和批准后只对新获准上下文开放。保留冻结审批、未知动作和业务回执并继续对账，不能用删除审计、重置历史或扩大角色解决事件。
5. 0045提供不可变保留草稿、本人申请与一次元数据影响预览及未来tombstone结构，没有实际批准/清理/擦除和备份删除传播服务。真实擦除须独立明确授权、范围和保留规则；普通 ORM 软删除不是擦除，不在故障处理期间删除数据库/备份或放开物理删除保护。
6. 恢复记录包含根因、修复版本、仍未知的结果、负责人角色和恢复范围。外部通知按用户授权和组织既有机制处理，本实现没有自动外部告警/消息发送渠道。
