## Context

仓库采用 FastAPI、SQLAlchemy/Alembic、PostgreSQL、React/TypeScript，并已有租户身份、组织、Agent 草稿/版本/发布、审计事件和管理端分页模式。知识问答目前没有正式知识模型，工具目录也不能替代文档发布和 ACL。产品基线要求回答只引用已发布、权限允许、有效且可定位版本/章节的内容。

本 change 横跨数据库、领域服务、管理 API、前端和审计。它只形成可信知识快照，不实现 Embedding、向量索引、Rerank 或 Agent 回答。

## Goals / Non-Goals

**Goals:**

- 建立租户隔离的知识源、文档和不可变版本模型。
- 提供可审计、可并发控制的草稿、审核、发布、失效、归档和回滚流程。
- 使用服务端 ACL 和有效期约束管理访问，并为检索提供稳定快照。
- 提供与现有控制面一致的管理 API、分页、错误契约和最小前端流程。
- 支持导入 P0 候选知识清单，同时禁止将 Mock 内容误标为生产知识。

**Non-Goals:**

- 不实现向量数据库、分块检索、Rerank、查询改写或答案生成。
- 不接入外部 CMS、对象存储或生产知识数据源。
- 不支持模型自主发布、修改 ACL 或绕过审核。
- 不在本 change 中实现自动知识更新和冲突自动解决。

## Decisions

### 1. 稳定文档身份与不可变版本分离

`KnowledgeSource` 表示来源及治理归属，`KnowledgeDocument` 保存稳定身份和当前状态，`KnowledgeVersion` 保存不可变标题、正文、内容哈希、章节锚点和版本元数据。已发布版本不得原地修改；更新必须创建新版本。

替代方案是直接覆盖文档正文。该方式简单，但无法保证历史引用、审计和运行时快照可复现，因此不采用。

### 2. 服务端状态机控制发布

版本状态采用 `draft -> in_review -> published -> superseded/retired`，文档可进入 `archived`。提交审核、发布、失效和回滚均由领域服务在事务中校验；回滚通过复制历史快照创建新版本，不重新激活可变历史记录。

发布请求携带期望修订号，使用行锁/乐观并发检查，确保同一文档不会并发产生两个当前发布版本。

### 3. ACL 采用允许列表且默认拒绝

每个文档保存受众类型，并可关联角色、组织单元和显式主体范围。访问判定同时要求租户匹配、主体有效、至少命中一条允许规则、版本已发布且在生效期内。平台管理员的管理权限不能自动扩大其业务知识访问范围，审计员仅能读取授权审计元数据。

替代方案是把 ACL 文本传给模型判断。模型判断不可作为安全边界，因此不采用。

### 4. 发布时生成确定性检索快照

发布事务生成只读 `KnowledgeSnapshot` 元数据，包括租户、文档、版本、内容哈希、标题、章节锚点、ACL 摘要、有效期和发布时间。后续检索只消费快照 ID 和不可变内容，不查询草稿。

本 change 不生成向量，但在发布/失效后发出事务内 outbox 事件，供后续索引器幂等处理。若当前项目尚无通用 outbox，则先记录持久化待处理事件，不以进程内消息作为唯一事实来源。

### 5. 复用现有管理端与审计模式

管理 API 使用 `/api/admin/knowledge-sources` 和 `/api/admin/knowledge-documents`，沿用现有认证、租户过滤、分页和统一错误响应。审计沿用既有不可变事件模式，扩展资源类型和动作，不在日志中保存完整敏感正文。

前端新增 `/knowledge` 列表与详情页，覆盖加载、空数据、错误、禁用、窄屏和键盘操作。发布/失效/回滚使用确认对话框，展示影响版本与状态。

### 6. 内容格式与边界

P0 正文接受 UTF-8 Markdown，服务端限制单版本大小并计算 SHA-256；章节锚点由确定性解析器生成并校验唯一性。HTML 渲染必须消毒。附件、OCR 和二进制解析留给后续 source adapter change。

## Risks / Trade-offs

- [ACL 规则过细导致查询复杂] → 发布时生成规范化 ACL 摘要，并为 tenant/status/effective time 建索引；先以正确性优先。
- [并发发布导致双活动版本] → 事务锁、期望修订号和数据库唯一约束共同保护。
- [知识过期仍被检索] → 查询时再次校验有效期，发布/失效事件驱动索引更新，并暴露过期/待复核状态。
- [Mock 内容进入企业试运行] → 来源和环境标记必填，P1 发布门禁拒绝 `mock` 来源进入 production。
- [正文写入审计导致敏感信息泄露] → 审计仅保存资源 ID、版本、内容哈希和字段差异摘要。
- [数据库保存 Markdown 增长过快] → P0 以受限文档规模换取一致性；达到测量阈值后再评估对象存储。

## Migration Plan

1. 新增枚举、数据表、索引、约束和表/字段注释；迁移不回填生产数据。
2. 实现领域服务、ACL 判定、状态机、审计和 outbox 事件。
3. 增加管理 API 和内部已发布快照读取接口。
4. 增加前端管理流程并导入可选的 P0 Mock 清单。
5. 运行单元、API、租户隔离、并发发布、迁移和浏览器端验证。

回滚时先停止知识写入和索引消费者，再回滚应用版本；若已存在知识数据，数据库降级前必须导出快照并确认删除影响，不自动执行破坏性降级。

## Open Questions

- P1 的外部知识源适配器、同步频率和冲突策略由后续 change 决定。
- 生产单文档大小与保留版本数需根据 P0 测量结果确定。
- 是否复用现有 `agent_audit_events` 表或抽象通用审计表，在实现前依据当前迁移兼容性决定，但 API 审计契约保持一致。
