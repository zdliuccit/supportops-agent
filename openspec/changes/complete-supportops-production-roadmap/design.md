## Decisions

### 1. 总规划按工作流实施，历史 change 保留所有权

总 change 提供共同契约与任务依赖；每次实施选择一个明确工作流，可按其范围拆分后续 change，并将任务归属回写到总清单。`add-knowledge-lifecycle` 的 4 项和 `add-system-agent-dashboard` 的 16 项先做现状复核，已存在代码只补验收；缺失部分留在原 change 交付，新任务仅引用并消费其结果。

替代方案是把所有旧任务重新复制为新增功能，容易双重统计与重复开发；或者只列高层 TODO，无法证明覆盖，均不采用。历史任务“完成”必须有实际测试/验收证据，规划生成期间不改旧勾选状态。

### 2. 以现有模块化单体增加可靠性契约

先复用 PostgreSQL、Redis、LangGraph 与共享核心包，分别管理服务租约、Run 执行尝试与通知 Outbox。每次尝试有 owner、租约、递增 generation/fencing token 和执行结果；事件、产品消息、观测关联 attempt，旧执行者不能覆盖新执行者终态。

消息/Run/Outbox 在同一数据库事务提交；Outbox 分发至少一次，消费以数据库状态为准。恢复扫描分批、确定排序、有限重试并有死信/人工诊断入口。ACK 或 Redis Streams 不是预先强制选型，需以丢失投递、重复投递和恢复测试证明策略。

W04.3分批领取补齐（2026-10-18）：原分发每次重查最早一条通知，再阻塞锁Run，多个Worker可能共同等待相同队首；仅通知行SKIP LOCKED不能消除前面的Run等待。现在单次只读发现next_attempt_at/id排序的有限候选ID/Run/tenant（默认20，配置1–100，调用limit只能降低），结束发现事务，再每条独立事务按Run→Outbox顺序SKIP LOCKED并复检绑定/到期/状态和原会话/配额/次数/窗口。忙或陈旧候选不消费次数、不标废弃，继续本批下一项；不在Redis调用期间持有整批锁，也不保存虚构owner/领取许可。API仍限原Run且limit=1，Worker复用；Redis成功/提交未知仍至少一次，同一Run UUID不重建输入。之前单条提交不受后续失败回滚，新到期留下一次，未承诺全队无饥饿、表锁或驱动清理硬截止。SKIP LOCKED用于队列类多消费者的行锁语义见[PostgreSQL官方说明](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)。无新表/接口/依赖/迁移，分发源码纳入新发布清单；重复/多Worker/取消故障验收暂缓，4.3及163/302保持。

服务心跳、消费调度、恢复/健康刷新/清理独立运行；每 Worker 有界并发、队列背压、租户配额和优雅停机。模型探测使用独立 job 类型与队列/执行器入口，避免占用聊天会话状态或 HTTP 进程内 BackgroundTasks 作为唯一事实。

替代方案为立即引入 Temporal/专用 Agent Server；先通过长任务等待、恢复复杂度和运维成本评估，再决定是否替换调度实现，能力契约不依赖某个引擎。

### 3. 会话执行串行，checkpoint 也受恢复边界保护

同 tenant/conversation 的用户消息确定排序，单会话仅允许一个可执行 attempt，其余显式排队；历史快照止于该 Run 输入位置。不同会话可并发；取消是独立状态信号，任务在模型/工具调用边界和等待/输出期间协作响应。

业务数据库 fencing 不能自动阻止旧 Worker 写 checkpoint 或调用外部系统。实施必须同时设计 checkpoint attempt namespace/提交指针或受控 saver 写入门禁，并验证租约失效后旧执行者无法污染当前会话；若底层无法安全隔离，先隔离/确认终止旧执行者再转移执行，不能仅重置 Run 为 queued。外部副作用另受动作幂等与连接器有效授权保护。

checkpoint 已写而产品消息未提交时，对应 attempt 标为不一致并隔离状态；以产品事实及有效提交指针恢复，不删除其他 attempt 的有效状态。异常恢复不能盲目重放已执行工具。

### 4. 版本用于复现，当前授权决定是否允许执行

保存 Agent/模型/工具/Prompt/知识/策略版本和创建时主体快照；调用前重新加载当前用户状态、租户、Agent grant、工具启停和资源范围。目录元数据与执行策略由统一服务解析，Prompt、模型或静态注册表不能作为最终权限裁决。

风险使用既有 R0–R4 产品规范，由服务端基于工具能力、参数、目标资源与数据敏感度判定。旧 `low/medium/high` 保留展示兼容并制定保守映射；未经验证的高风险定义不得自动降级。审批只允许合法权限内的动作，不能成为扩权令牌。

单工具限额、并发许可、Run/租户预算在统一边界实施并有原子计数。管理员目录编辑追加审计；紧急停用影响旧 Agent 版本及已排队 Run。旧固定版本依旧可复现，但授权、凭据撤销或数据有效期变化可以阻止继续执行。

### 5. 工具目录、网关、连接器职责分离

目录保存允许接入的可信工具版本、Schema、来源、风险与适配配置；统一网关负责每次请求授权、输入校验、额度、审批、调用、结果过滤与审计；连接器只实现本地/API/MCP 协议和目标业务语义。Registry 是治理与发现能力，不位于实际业务执行末端。

MCP 工具列表先经过来源信任与 allowlist 筛选，版本变化需重新校验。远程描述/annotations 不作为可靠权限或风险结论；HTTP 授权遵循所采用协议版本，不把平台用户 JWT 任意转发给外部服务。网关与连接器执行出站地址、重定向、大小/超时、租户隔离和凭据作用域检查。

W08.8实际交付（2026-10-15）：outbound_http提供固定服务器目标的HTTPS JSON传输边界，精确IDNA域名/端口允许集合、全部DNS地址检查、可选确切IP集合、RFC1918/ULA逐IP例外、固定IP连接/原主机TLS与Host校验。回环/link-local/保留/组播/未指定地址始终拒绝，禁任意头/代理/重定向/压缩/隐式重试；解析在无应用环境/有限输出的可终止标准库子进程运行，整体时限覆盖DNS和网络。OTLP发送复用，保留原租户/显式IP/错误域，没有实际联网。原模型SDK专属策略不改，真实业务适配器/权限凭据/OS隔离仍待；有界原始bytes仍须固定输出Schema与脱敏，helper本身不授予业务权限或判定未知写结果。测试/网络验收继续暂缓。

W08.9实际交付（2026-10-15）：现有已注册输出统一严格JSON/封闭Schema/对象根/重复键与非有限数拒绝/深度16节点4096有界检查，运输与领域状态核对；未知输出不启用。通过Schema后的全部文本字段用共用redaction和本轮已知秘密精确值遮蔽，源ID/digest/key不可改写，需脱敏则拒绝；认证头/Cookie的完整值和多行PEM不只遮第一段。知识增加可空content_is_redacted区分本次脱敏和预算excerpt，原分块摘要和来源复检不改，旧未知不补造。网关删除重复字节截断，严格复检/完整序列化后超限整份拒绝；返回异常链不携原始输入，SDK元数据不透传。继续以真实账本摘要和model_tool_data_v1来源/时效/冲突门禁隔离不可信数据，不能用文本取得执行许可，不声称通用语义注入检测。真实远程适配器/输出注册和测试验收仍待，无新依赖/表/迁移或实际外部调用。

复用 `SecretProvider` 引入 provider factory；本地密封用于 local/test，production 按选型对接 Vault/KMS 与短期租户/用户凭据。连接器隔离凭据，模型上下文及可执行不可信内容均不能读取秘密。

### 6. 先可信知识，再动态检索

先验收既有版本/ACL/并发/审计和发布事件，再消费知识 Outbox。索引记录 document/version/snapshot、content digest、section anchor、embedding 模型版本和 generation；发布、取代、失效、归档、ACL 变化及到期均使索引更新或失效，失败可见且可重试。

检索先限制租户、主体和有效版本，候选正文读取时复检权限，最后才进入模型；缓存必须包含权限/版本维度且支持撤销失效。引用指向获准证据快照与段落，不由模型自行生成可信 URL。无依据、证据冲突或外部来源失败时追问/拒绝确定结论/升级。

先评测单次检索/pgvector 能力，再启用混合检索、重排或查询拆解；不得把这些全部设为固定昂贵流水线。外部来源使用增量游标、解析沙箱与可审阅新版本；自动更新初期只生成候选草稿，未经发布流程不得进入正式索引。

### 7. 上下文、结果与诊断都是显式业务数据

上下文区分完整历史、当前模型输入、证据集与经确认的长期记忆；裁剪保留当前问题、已确认事实、来源时间和未解决事项。预算在每次调用前计量系统 Prompt、历史、工具 Schema/结果、证据与输出预留，并计入重试/回退；未知价格不能默默绕过费用硬限制。

助手结果采用版本化持久化对象，保存 answer、summary、合法引用、建议动作和升级状态；动作建议不是已执行结果。保留现有正文/SSE 恢复接口，新增结果就绪事件不泄露工具参数/隐藏推理；旧正文消息按兼容策略展示，不伪造历史引用。

429 流程是同一 Runtime 内的显式节点：分类 → 请求信息 → 受限只读查询 → 知识规则 → 证据判断 → 回答/升级。产品 P0 使用 4–6 个固定 Mock 只读工具；接真实日志、账户/配额、路由/故障前需要目标系统契约与资源范围。模块可共享事实契约，但不共享无边界可变上下文。

### 8. 业务动作状态与 Run 状态分开

动作持久化名称、参数哈希、风险、申请主体、幂等键、外部业务 ID/回执、调用尝试和复核结果。Run 可有 waiting_approval/reconciling；动作可为 proposed/waiting/authorized/executing/succeeded/failed/unknown/reconciled。具体枚举及状态迁移在迁移任务中固定，旧终态保持兼容。

R2–R4 写动作先记录幂等意图，再调用连接器。超时/丢失响应进入 unknown，先查询外部最终状态；只有确认未执行且策略允许才使用同一逻辑动作键重试，不能用新 Run/新模型请求生成新键绕过去重。独立只读复核证明业务状态；无法证明时人工接管，不宣称成功。补偿作为新受控动作，不能无条件自动执行。

低风险建单可按批准策略自动执行，不依赖后续高风险审批才能交付 P0；R4 模拟验收必须在审批完整实现后执行。工单连接器从 Mock 开始，优先选一个真实系统，支持受限查询、幂等建单、更新和回调去重，避免同时承诺 CRM/Jira 等所有适配。

### 9. 审批等待不占 Worker，恢复后再次授权

审批绑定租户、Run/action、工具版本、规范化参数哈希、申请/审批主体、有效期和一次性使用状态；非本人且有范围权限的审批人可以批准/拒绝。等待持久化 checkpoint 与业务状态后释放执行资源。

审批 API/恢复通知采用幂等与事务 Outbox；批准后再次检查身份、授权、参数与凭据。参数修改创建新提案/新审批；停用、撤销、过期和取消拒绝继续执行。一次性消费与动作状态在事务中协调，外部执行不声称与数据库全局原子，仍依赖动作幂等和对账。

W06.5 当前等待规则：同会话 waiting_approval/waiting_action 仍是未结束输入，会话最早 input_sequence 门禁继续阻止后轮执行；API 可以幂等接收后续输入并保存 queued，但不能插队形成模型追问或修改当前冻结动作。现有 Web 聊天保持输入禁用并展示等待，可读取本人当前获准证据/动作/升级包或处理审批；新模型只读追问需要前轮终止后排队执行，或用户明确另开授权会话，不自动开新会话绕过等待。等待期间无需占用模型 Worker，其他会话按租户额度继续。

参数更改只走显式 amend：复检当前主体/工具/资源/非本人审批者、generation/参数摘要/目录版本，创建带 supersedes_action_id 的新提案/新审批，原批准失效而不是覆写。已有执行 attempt/审批消费，或 unknown/reconciling/needs_attention 等副作用状态时拒绝换参数/换业务键，先对账；标题/摘要也不能含凭据。批准恢复仅动作阶段、终态解除最早输入阻塞后允许原 queued 后轮，旧轮问题与 checkpoint 输入边界不重写。

### 10. 观测、评测和发布形成闭环

### 14. W27 本地 Markdown 候选读取与预览

`knowledge_markdown_source.py`提供库函数`preview_local_markdown`，不设置默认目录或API/Worker入口。具体来源仍待27.1确认；以下是可复用候选实现，不构成来源批准或真实导入。调用方必须从可信配置传入绝对根目录、精确相对文件清单、预期清单摘要和固定IngestionScope；清单摘要须匹配scope.source_contract_digest，身份/适配器/解析摘要须匹配实际候选版本。摘要仅冻结数据，不能代替当前人员/来源批准与知识ACL授权。根目录/清单含路径信息，应保存在受控配置，不写普通审计或暴露给模型。

结果与限制：内存批次绑定scope/清单摘要，每对象含跨Job稳定对象键、原始字节SHA-256、规范正文SHA-256、字节数及不可变正文/锚点；默认repr隐藏路径/正文/锚点/对象集合，错误只用固定码。不输出绝对路径、原始OS异常或自动保存文件；显式序列化预览仍会包含正文，调用方须按知识正文权限处理，repr隐藏不代表加密或防泄露。没有来源版本就不从mtime伪造版本序列，不从文件mode/owner推导知识用户/角色/部门ACL；未知权限不产生可发布内容。整批失败不返回部分结果，不生成成功页回执/推进游标或创建KnowledgeVersion。

### 54. W8.7 固定公钥JWT访问令牌验签

此前没有清理批次执行边界。新增retention_batch_contracts/runtime内部库，计划冻结原租户/本人/申请、类别/操作、政策/批准/新盘点/独立账本与维护身份，最多100个排序唯一资源摘要。批准摘要并非许可：当前authority必须另行复查真实原批准、法律保留、完整依赖、在途引用和精确目标，草稿和预览均不转换为批准。无默认Store/authority/类别执行器或验证器，依赖缺失直接拒绝，不增加API、Worker或后台调度。

可信Store接口要求领取事务有限锁、固定计划/序号与同主体串行、最多三次且仅未派发可证明安全的显式领取恢复，提交owner/generation/最长30秒租约。协调器核对租约/计划后要求先独立持久提交claimed到dispatched的唯一CAS，再复核当前许可才调用一次固定执行器；不得复用一般只读Run重试。已派发/未知/取消不重新调用执行器，失去租约不能续租后重放。此节最初描述协调器契约，后续独立PG Store实现见第68节；初始接口说明不代表数据库实现当时已存在。

提交回执不代表完成：单独verifier身份只读观察同一精确集合，结果固定计划/租约/generation/验证ID及真实观察时间。Store必须围栏最新验证ID、累计最多三次验证，原子保存已确认项的真实tombstone/原验证/最小审计与终态后返回匹配回执；资源/操作/证据/事实摘要错配拒绝。仅全部verified为completed，全未执行为not_executed，部分/未知为needs_attention；全局job_complete和自动重放许可恒false。未完成前批不可推进下一序号，原事实及终态不可因未知回执覆盖。

协调器只执行一批，整体工作等待10秒、显式只读复核8秒；边界1秒、目标执行/观察2秒并按原计划/租约剩余时间裁剪。普通异常固定未确认码，追加未知事件最多0.5秒且不掩盖原结果；外部取消传播，驱动清理或不合作适配器不承诺硬截止。未来目标写事务仍须自行复检当前许可、围栏和依赖，不能仅靠协调器外层检查解决目标事务竞争。实际持久Store/身份/政策、类别及副本适配、状态查询和恢复许可均未接，本轮只交付协调代码及契约，无真实删除或事实生成，21.3及169/302保持未完成。

## Risks / Trade-offs

- [总规划规模较大] → 按工作流/依赖选择实施范围；每次交付引用任务 ID，避免一次性部署全项目。
- [新 enum/分页/结构化结果破坏旧客户端] → 先扩展响应与兼容读取，再同步 Web；对需迁移的接口明确版本切换窗口。
- [fencing 只覆盖数据库，旧 Worker 继续写 checkpoint/外部系统] → checkpoint 隔离与执行者生命周期控制、动作幂等、凭据撤销及故障注入共同验收。
- [等待审批占用会话执行锁] → 持久化等待；明确允许的只读交互/后续消息队列，恢复后仍维持动作参数与版本边界。
- [权限变化导致索引与缓存泄露] → 正文入上下文前复检 ACL/有效期；撤销触发失效，缓存不能按查询词全局复用。
- [工作流引擎看似保证 exactly-once] → 外部动作仍使用业务幂等、回执与对账；不承诺跨系统全局一次执行。
- [真实系统契约、成本或审批角色未确定] → 决策任务前置，Mock/沙箱验证先行；不伪造生产成功。
- [长期记忆或自动知识把幻觉固化] → 确认、来源、审批发布、纠错、删除和隔离评测。
- [指标/日志包含敏感信息] → 白名单、参数哈希、作用域、保留期与脱敏；不记录隐藏推理。
- [历史任务与归档规范有重复] → 覆盖矩阵标明唯一验收所有权；通过证据核对，不直接改旧勾选。

### 执行尝试与输入边界

`RunAttempt` 使用独立 UUID、Worker 启动 owner、单调 generation、heartbeat/lease 和尝试终态；Run 保存 current_attempt_id 与 generation，会话保存 active_run/active_attempt 执行许可。所有领取/产品写入/正文事件/续租/恢复按会话→Run→attempt→通知加锁，核对当前指针、owner、generation、有效租约；已失效执行者只能写自己的历史观测，不能更新产品状态。

每个 attempt 使用 `tenant/conversation/run/attempt` 独立 thread，不复制或继续失败 attempt 的内部图。新尝试从本轮输入序号范围内的产品消息重建，已完成轮的助手回答按所属输入序号排列。产品提交同时保存成功 attempt、助手结果与会话 checkpoint 精确指针；未提交状态只是隔离历史，恢复不删除其他尝试的有效 checkpoint。相比复制 checkpoint 的内部 channel/pending-writes，产品重建牺牲未提交图的细粒度续跑，但避免框架内部恢复细节和未知工具重放；当前采用这一策略。
