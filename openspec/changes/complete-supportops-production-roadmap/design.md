## Context

本规划以根 `AGENTS.md` 的 2026-10-12 快照为依据：3 个应用、1 个共享核心包、12 个逻辑模块和 29 张业务 ORM 表。已有 API/控制面、单 Agent Run、消息、事件、checkpoint、知识生命周期和应用内观测；当前没有真实知识检索、业务动作记录、持久化审批或生产运维闭环。

本目录作为总规划入口，`tasks.md` 是分工作流的可执行清单，`README.md` 提供需求覆盖与历史任务映射。所有新任务均保持未勾选。已有 change 的 `[x]` 只作为既有记录，不能替代当前实际验收；旧 change 的 20 项 `[ ]` 不在本次直接重写。

相关规范：`support-product-scope`、`support-risk-policy`、`support-release-gates`。首个业务域保持 API 支持/429，产品 P0 使用单 Agent 和隔离 Mock；真实企业系统与审批属于 P1；路由、子 Agent、在线评测、自动更新与 HA 按 P2 启动门禁推进。工程优先级 P0/P1/P2 与产品阶段独立记录。

## Goals / Non-Goals

**Goals:**

- 覆盖 AGENTS 所有待处理差距、已有 20 项未验收清单及目标图的必要能力，提供清晰的依赖与验收路径。
- 修复执行与授权底座后形成知识回答、429 诊断、工单升级和依赖失败降级四条可验收主路径。
- 为外部副作用建立授权、审批、幂等、复核、对账和人工接管闭环。
- 建立数据、模型、知识、工具、Prompt、策略和评测版本的可追踪关系；保留旧会话语义。
- 对可选能力明确启动证据、产品决策、实现前提和默认关闭状态，使规划全面但不形成无条件生产承诺。

**Non-Goals:**

- 本次不写业务代码、不执行迁移、不安装依赖、不连接生产系统、不导入真实工单或凭据、不提交/推送/部署。
- 不重新实现已具备且验收通过的登录、组织、Agent/模型 CRUD、聊天或 Dashboard 基础；未通过的部分以差距修复处理。
- 不允许模型上传任意代码、自由构造执行图、生成生产 SQL、自动建号扩权、任意联网或直接自动发布知识。
- 不因图中有某个方框就增加微服务、消息中间件、独立向量库或工作流引擎；不强制所有请求经过全部业务模块。
- 不在没有业务批准的情况下引入退款/封禁等真实操作；P1 的 R4 演练使用隔离业务替身。
- 不把工作项勾选、artifact 完备或 mock 测试通过写成生产验收通过；归档需实际实现、验收并遵循用户授权。

## Decisions

### 1. 总规划按工作流实施，历史 change 保留所有权

总 change 提供共同契约与任务依赖；每次实施选择一个明确工作流，可按其范围拆分后续 change，并将任务归属回写到总清单。`add-knowledge-lifecycle` 的 4 项和 `add-system-agent-dashboard` 的 16 项先做现状复核，已存在代码只补验收；缺失部分留在原 change 交付，新任务仅引用并消费其结果。

替代方案是把所有旧任务重新复制为新增功能，容易双重统计与重复开发；或者只列高层 TODO，无法证明覆盖，均不采用。历史任务“完成”必须有实际测试/验收证据，规划生成期间不改旧勾选状态。

### 2. 以现有模块化单体增加可靠性契约

先复用 PostgreSQL、Redis、LangGraph 与共享核心包，分别管理服务租约、Run 执行尝试与通知 Outbox。每次尝试有 owner、租约、递增 generation/fencing token 和执行结果；事件、产品消息、观测关联 attempt，旧执行者不能覆盖新执行者终态。

消息/Run/Outbox 在同一数据库事务提交；Outbox 分发至少一次，消费以数据库状态为准。恢复扫描分批、确定排序、有限重试并有死信/人工诊断入口。ACK 或 Redis Streams 不是预先强制选型，需以丢失投递、重复投递和恢复测试证明策略。

服务心跳、消费调度、恢复/健康刷新/清理独立运行；每 Worker 有界并发、队列背压、租户配额和优雅停机。模型探测使用独立 job 类型与队列/执行器入口，避免占用聊天会话状态或 HTTP 进程内 BackgroundTasks 作为唯一事实。

替代方案为立即引入 Temporal/专用 Agent Server；先通过长任务等待、恢复复杂度和运维成本评估，再决定是否替换调度实现，能力契约不依赖某个引擎。

### 3. 会话执行串行，checkpoint 也受恢复边界保护

同 tenant/conversation 的用户消息确定排序，单会话仅允许一个可执行 attempt，其余显式排队；历史快照止于该 Run 输入位置。不同会话可并发；取消是独立状态信号，任务在模型/工具调用边界和等待/输出期间协作响应。

业务数据库 fencing 不能自动阻止旧 Worker 写 checkpoint 或调用外部系统。实施必须同时设计 checkpoint attempt namespace/提交指针或受控 saver 写入门禁，并验证租约失效后旧执行者无法污染当前会话；若底层无法安全隔离，先隔离/确认终止旧执行者再转移执行，不能仅重置 Run 为 queued。外部副作用另受动作幂等与连接器有效授权保护。

checkpoint 已写而产品消息未提交时，对应 attempt 标为不一致并隔离状态；以产品事实及有效提交指针恢复，不删除其他 attempt 的有效状态。异常恢复不能盲目重放已执行工具。

### 4. 版本用于复现，当前授权决定是否允许执行

保存 Agent/模型/工具/Prompt/知识/策略版本和创建时主体快照；调用前重新加载当前用户状态、租户、Agent grant、工具启停和资源范围。目录元数据与执行策略由统一服务解析，Prompt、模型或静态注册表不能作为最终权限裁决。

风险使用既有 R0–R4 产品规范，由服务端基于工具能力、参数、目标资源与数据敏感度判定。旧 `low/medium/high` 保留展示兼容并制定保守映射；未经验证的高风险定义不得自动降级。审批只允许合法权限内的动作，不能成为扩权令牌。

单工具限额、并发许可、Run/租户预算在统一边界实施并有原子计数。管理员目录编辑追加审计；紧急停用影响旧 Agent 版本及已排队 Run。旧固定版本依旧可复现，但授权、凭据撤销或数据有效期变化可以阻止继续执行。

### 5. 工具目录、网关、连接器职责分离

目录保存允许接入的可信工具版本、Schema、来源、风险与适配配置；统一网关负责每次请求授权、输入校验、额度、审批、调用、结果过滤与审计；连接器只实现本地/API/MCP 协议和目标业务语义。Registry 是治理与发现能力，不位于实际业务执行末端。

MCP 工具列表先经过来源信任与 allowlist 筛选，版本变化需重新校验。远程描述/annotations 不作为可靠权限或风险结论；HTTP 授权遵循所采用协议版本，不把平台用户 JWT 任意转发给外部服务。网关与连接器执行出站地址、重定向、大小/超时、租户隔离和凭据作用域检查。

复用 `SecretProvider` 引入 provider factory；本地密封用于 local/test，production 按选型对接 Vault/KMS 与短期租户/用户凭据。连接器隔离凭据，模型上下文及可执行不可信内容均不能读取秘密。

### 6. 先可信知识，再动态检索

先验收既有版本/ACL/并发/审计和发布事件，再消费知识 Outbox。索引记录 document/version/snapshot、content digest、section anchor、embedding 模型版本和 generation；发布、取代、失效、归档、ACL 变化及到期均使索引更新或失效，失败可见且可重试。

检索先限制租户、主体和有效版本，候选正文读取时复检权限，最后才进入模型；缓存必须包含权限/版本维度且支持撤销失效。引用指向获准证据快照与段落，不由模型自行生成可信 URL。无依据、证据冲突或外部来源失败时追问/拒绝确定结论/升级。

先评测单次检索/pgvector 能力，再启用混合检索、重排或查询拆解；不得把这些全部设为固定昂贵流水线。外部来源使用增量游标、解析沙箱与可审阅新版本；自动更新初期只生成候选草稿，未经发布流程不得进入正式索引。

### 7. 上下文、结果与诊断都是显式业务数据

上下文区分完整历史、当前模型输入、证据集与经确认的长期记忆；裁剪保留当前问题、已确认事实、来源时间和未解决事项。预算在每次调用前计量系统 Prompt、历史、工具 Schema/结果、证据与输出预留，并计入重试/回退；未知价格不能默默绕过费用硬限制。

助手结果采用版本化持久化对象，保存 answer、summary、合法引用、建议动作和升级状态；动作建议不是已执行结果。保留现有正文/SSE 恢复接口，新增结果就绪事件不泄露工具参数/隐藏推理；旧正文消息按兼容策略展示，不伪造历史引用。

429 流程是同一 Runtime 内的显式节点：分类 → 请求信息 → 受限只读查询 → 知识规则 → 证据判断 → 回答/升级。产品 P0 使用 4–6 个固定 Mock 只读工具；接真实日志、账户/配额、路由/故障前需要目标系统契约与资源范围。模块可共享事实契约，但不共享无边界可变上下文。

### 8. 业务动作状态与 Run 状态分开

动作持久化名称、参数哈希、风险、申请主体、幂等键、外部业务 ID/回执、调用尝试和复核结果。Run 可有 waiting_approval/reconciling；动作可为 proposed/waiting/authorized/executing/succeeded/failed/unknown/reconciled。具体枚举及状态迁移在迁移任务中固定，旧终态保持兼容。

R2–R4 写动作先记录幂等意图，再调用连接器。超时/丢失响应进入 unknown，先查询外部最终状态；只有确认未执行且策略允许才使用同一逻辑动作键重试，不能用新 Run/新模型请求生成新键绕过去重。独立只读复核证明业务状态；无法证明时人工接管，不宣称成功。补偿作为新受控动作，不能无条件自动执行。

低风险建单可按批准策略自动执行，不依赖后续高风险审批才能交付 P0；R4 模拟验收必须在审批完整实现后执行。工单连接器从 Mock 开始，优先选一个真实系统，支持受限查询、幂等建单、更新和回调去重，避免同时承诺 CRM/Jira 等所有适配。

### 9. 审批等待不占 Worker，恢复后再次授权

审批绑定租户、Run/action、工具版本、规范化参数哈希、申请/审批主体、有效期和一次性使用状态；非本人且有范围权限的审批人可以批准/拒绝。等待持久化 checkpoint 与业务状态后释放执行资源。

审批 API/恢复通知采用幂等与事务 Outbox；批准后再次检查身份、授权、参数与凭据。参数修改创建新提案/新审批；停用、撤销、过期和取消拒绝继续执行。一次性消费与动作状态在事务中协调，外部执行不声称与数据库全局原子，仍依赖动作幂等和对账。

### 10. 观测、评测和发布形成闭环

本轮 callback/attempt 事实用于模型与工具统计，不把 checkpoint 历史消息重复计费。记录首模型输出与客户端收到首文本两个指标；客户端上报仅为受限性能观测，不能决定业务完成。等待审批时间与实际执行时间分开，恢复/对账可下钻到具体尝试。

Dashboard 保留原租户/时间/Agent 口径，完成历史筛选、下钻、排行、缺失值和窄屏验收。OpenTelemetry exporter 可作为映射层，业务审计事实留在数据库，约定版本单独管理。

复用 S01–S20 与评测基线，建立至少 60 个正/边界/升级样本及固定 Mock 结果，版本化 Prompt/模型/知识/工具/策略和负载。初始阈值沿用既有规范，不在实施中随意降低；高风险绕过、跨租户与严重泄露为零容忍门禁。发布先评测，再允许新版本灰度给新会话；原会话继续固定版本，回滚停止新激活/副作用而不覆写历史。

### 11. 企业集成、数据治理与规模化采用启动门禁

先移除登录预填，评估浏览器令牌与会话失效契约；refresh token 不是默认必选，可明确使用短期令牌重登或服务端安全会话。企业 SSO/委托 OAuth 先确定客户 IdP、显式映射和最小范围；保留本地管理员应急路径，不以外部声明自动扩权。

长期记忆、动态模型路由、专业 Agent、额外渠道、A2A、在线评测、自动知识更新、HA 分别要求业务需求/基线瓶颈/质量安全验证和责任人记录。拒绝启动仍保留需求与后续实现任务为候选，不能以“决策完成”冒充“功能完成”。

新路由策略固定到 AgentVersion 并解析允许模型版本集合；旧版本仍固定原模型。每次真实模型选择记于调用观测，不能在故障时默默使用最新配置/凭据。专业子 Agent 权限与预算不超过父任务，优先只读并行，写动作仍经统一网关。

数据保留覆盖消息、checkpoint、事件、观测、凭据 revision、知识/记忆/外部回执与备份。软删除不是擦除；明确保存期限、法律保留、可授权擦除和备份恢复后重新施加删除标记。不能为擦除需求移除普通业务 ORM 的软删除保护，应建立独立、可审计、受控的维护流程。

## Risks / Trade-offs

- [总规划规模较大] → 按工作流/依赖选择实施范围；每次交付引用任务 ID，避免一次性部署全项目。
- [新 enum/分页/结构化结果破坏旧客户端] → 先扩展响应与兼容读取，再同步 Web；对需迁移的接口明确版本切换窗口。
- [fencing 只覆盖数据库，旧 Worker 继续写 checkpoint/外部系统] → checkpoint 隔离与执行者生命周期控制、动作幂等、凭据撤销及故障注入共同验收。
- [等待审批占用会话执行锁] → 持久化等待；明确允许的只读交互/后续消息队列，恢复后仍维持动作参数与版本边界。
- [权限变化导致索引与缓存泄露] → 正文入上下文前复检 ACL/有效期；撤销触发失效，缓存不能按查询词全局复用。
- [工作流引擎看似保证 exactly-once] → 外部动作仍使用业务幂等、回执与对账；不承诺跨系统全局一次执行。
- [真实系统契约、成本或审批角色未确定] → 决策任务前置，Mock/沙箱验证先行；不伪造生产成功。
- [长期记忆或自动知识把幻觉固化] → 确认、来源、审批发布、纠错、删除和隔离评测。
- [指标/日志包含敏感信息] → 白名单、参数哈希、作用域、保留期与脱敏；不记录隐藏推理。
- [历史任务与归档规范有重复] → 覆盖矩阵标明唯一验收所有权；通过证据核对，不直接改旧勾选。

## Migration Plan

1. W00 建立当前证据、需求覆盖、旧任务映射与阶段责任；所有新增任务初始未勾选。
2. W01–W09 交付分页/会话安全、服务心跳、Outbox、Run 尝试/恢复、会话串行、实时授权、工具连接边界与上下文预算；对旧数据采用 expand/backfill/validate 流程。
3. W10–W14 交付结构化结果、知识验收/索引/检索、429 流程；P0 使用隔离 Mock 和单 Agent。
4. W15–W17 交付动作记录、审批与工单；按低风险建单/客服接管/高风险沙箱演练逐步启用，避免循环依赖。
5. W18–W23 完成观测/历史 Dashboard、评测、凭据隔离、留存、运维和版本门禁；按业务交付范围分批验收，不要求等所有工作流才上线任何低风险功能。
6. W24–W27 仅在对应启动决策通过后实施路由/记忆/子 Agent/渠道与规模化能力；W28 汇总发布级验收。
7. 回滚优先禁用新入口/新策略并停止新任务；保留历史 schema/记录，修复前对账在途动作。含历史数据的降级迁移、远程部署、生产擦除需明确授权，不能执行自动破坏性降级。

## Open Questions

所有问题均有 W00 或对应工作流的前置决策任务；它们不阻止本次生成规划，但会阻止依赖它们的生产集成。

- 企业 IdP、SSO/会话模式、审批角色与资源边界、凭据服务的目标产品及环境是谁提供？
- 首个真实工单/日志/账户/故障系统的 API、幂等/查询/回调契约与沙箱何时可用？
- embedding/重排模型的数据边界、版本、维度与定价；是否必须离线部署？
- Run 恢复是否需要引入专门持久化工作流引擎？现有 saver 如何实现 attempt 隔离与失效写入保护？
- 产品 P0/P1 的实际负载、SLO、RTO/RPO、留存/擦除/法律保留与租户配额怎样确认？
- 哪些 P2 候选有真实质量、成本或容量瓶颈证据；需要哪些额外渠道与独立 Agent 协作？
