## Why

当前仓库尚未形成可执行的产品基线，而参考设计同时覆盖 P0、P1、P2，若直接进入开发，容易出现范围失控、能力遗漏、验收口径不一致和高风险操作边界不清。现在需要先把产品定位、角色、场景、风险分级、发布边界和质量门槛固化为可追踪契约，作为后续 OpenSpec change 的共同上游。

## What Changes

- 定义平台服务的目标用户、核心价值、业务边界和第一阶段不做事项。
- 建立最终用户、客服、技术支持、审批人、知识管理员、平台管理员和审计员的职责边界。
- 定义 R0～R4 操作风险等级及自动执行、授权、审批和复核原则。
- 建立首批支持场景目录，并明确 429 API 错误诊断作为第一个端到端基准场景。
- 将整体能力划分为 P0 可用 MVP、P1 企业试运行和 P2 规模化生产三个发布层级。
- 定义功能、安全、质量和运维四类验收基线，以及指标如何建立、评审和调整。
- 建立后续能力 change 的依赖顺序和范围约束，但不在本 change 中实现应用功能。

## Capabilities

### New Capabilities

- `support-product-scope`: 定义产品定位、目标角色、业务边界、阶段范围及明确排除项。
- `support-risk-policy`: 定义支持场景中的权限原则、R0～R4 风险分级、审批边界及安全不变量。
- `support-scenario-baseline`: 定义核心问题目录、标准处理路径、升级条件和 429 基准场景。
- `support-release-gates`: 定义 P0/P1/P2 发布边界以及功能、安全、质量和运维验收门槛。

### Modified Capabilities

无。当前项目不存在已发布的 OpenSpec capability。

## Impact

- 新增 OpenSpec 产品基线规格，为后续会话运行时、知识库、检索、工具平台、Agent 编排、工单、人工接管、审批、安全审计和评测治理等 change 提供上游约束。
- 不修改应用代码、数据库、API、依赖或部署环境。
- 后续 change 必须引用本基线中的阶段边界、风险等级和验收要求；若产品范围或风险规则发生变化，应先更新对应 capability。
