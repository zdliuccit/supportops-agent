## Context

当前仓库只有项目简介，没有应用代码、数据模型、测试、部署配置或既有 OpenSpec capability。参考方案描述了从可用 MVP 到规模化生产的完整企业智能支持平台，覆盖会话、RAG、工具、LangGraph、工单、审批、安全、评测与运维。如果直接把整份方案转为一个开发 change，会产生边界过大、依赖不清和验收无法收敛的问题。

本 change 的利益相关者包括最终用户、客服、技术支持、审批人、知识管理员、平台管理员、审计员，以及负责产品规则、工程实现、测试和运维的团队成员。它建立的是产品治理与验收基线，而非运行时功能。

项目交付定位已确认为企业级智能支持产品。P0 是内部可用性里程碑，P1 企业试运行是近期交付目标，P2 规模化生产是基于试运行数据推进的演进目标；项目不以一次性演示或个人作品为验收标准。开发阶段可以使用 Mock 身份和 Mock 业务系统建立确定性基线，但 P1 必须接入企业认证、真实只读业务系统、持久化审计和接近生产的 staging 环境。

当前由项目作者一人承担产品、业务分析、Agent/后端、前端、测试质量、平台运维和安全评审等建设职责。规划和任务仍按这些职责边界分别记录，避免单人建设导致需求、实现和验收混为一体。自动化测试、固定评测集、审计证据和评审清单用于补偿缺少独立内部团队评审的风险；进入真实企业试运行前，仍需由目标企业的业务、安全和系统负责人确认其范围内的规则与接入。

单人建设只影响人员配置，不改变运行时职责分离。系统必须支持申请人、审批人和审计员使用不同身份；项目作者可以在非生产环境使用不同测试账号验证流程，但真实 R4 操作不得由同一业务主体申请并审批。

环境至少划分为 local、dev、staging 和 production，各环境使用隔离的身份、数据、密钥与外部系统配置。

约束：

- 当前处于 explore 模式，本 change 只允许沉淀规格和规划，不实现应用代码。
- P0 以单产品域、单 Agent 和 Mock 业务系统建立基线，P1 接入真实企业身份与只读业务系统。
- 单租户起步，但产品契约保留租户隔离语义。
- 权限、审批、金额、幂等和状态机必须由确定性服务控制，不能交给模型或 Prompt。
- 安全关键要求不可因演示范围、模型降级或交付时间而放宽。

## Goals / Non-Goals

**Goals:**

- 建立后续所有能力 change 共用的产品定位、角色、范围和术语基线。
- 将参考方案拆分为 P0、P1、P2，明确各阶段进入和退出条件。
- 固化 R0～R4 风险分类及不可绕过的授权、审批、幂等和审计原则。
- 定义首批支持场景应包含的信息，并把 429 API 错误诊断作为首个端到端基准。
- 使功能、安全、质量和运维要求能够映射为可重复验证的场景。
- 给后续 OpenSpec changes 提供依赖顺序和范围评审依据。

**Non-Goals:**

- 不创建前后端项目、数据库 Schema、API、Agent 图、Prompt 或部署环境。
- 不选择具体模型提供商、Embedding 模型、Reranker、认证提供商或云平台。
- 不把参考方案中的推荐目录结构视为已经确定的物理代码结构。
- 不承诺 P2 功能和日期。
- 不在本 change 中制作全部 20 个业务案例或 100～300 条评测数据；这里只定义其格式、数量下限和治理要求。
- 不实现或执行任何退款、补偿、封禁、删除等真实业务操作。

## Decisions

### 1. 使用二维规划，而不是只按技术层或单条场景规划

需求在“能力域”和“发布阶段”两个维度上管理。能力域保证整体方案不遗漏，发布阶段保证实际交付可以沿端到端链路逐步闭环。

替代方案：按前端、后端、数据库、AI 分工拆分。该方式适合任务分派，但不适合作为产品需求边界，因为任何一层都无法独立交付用户价值或完成验收。

### 2. 将产品基线拆成四个 capability

- `support-product-scope` 管理定位、角色和范围。
- `support-risk-policy` 管理权限、风险和安全不变量。
- `support-scenario-baseline` 管理业务问题、标准路径和升级包。
- `support-release-gates` 管理阶段边界与验收门槛。

替代方案：只建立一个 `support-product-baseline` capability。单一规格初期简单，但范围、风险、场景和发布治理的变化频率与审批人不同，后续容易产生大面积无关修改。

### 3. 以 AI/API 平台和 429 错误诊断作为首个产品域与基准场景

首批产品域确认为企业 AI/API 平台。场景基线覆盖限流配额、认证权限、请求模型、稳定性、客户端兼容、计费订单和密钥安全。429 场景能在范围可控的前提下同时验证知识解释、用户级限额、脱敏日志、渠道状态、故障事件、并行工具、证据冲突、引用和自动建单，是验证整体架构边界的高信息密度场景。

替代方案：先做纯 FAQ。纯 FAQ 能验证 RAG，但无法验证工具权限、实时证据、诊断和工单升级，容易形成不能扩展到企业闭环的聊天 Demo。

### 4. 将 P0、P1、P2 视为能力门禁而非固定日期

阶段完成取决于可观察行为和验收结果。时间计划可以调整，但安全不变量和阶段退出条件不能因工期自动豁免。

替代方案：直接采用固定八周计划。固定日历有利于沟通，但当前仓库、业务接口、知识文档和团队配置尚未就绪，日期无法作为可信基线。

### 5. 指标使用“初始目标 + 版本化测量口径”

参考方案的数值作为试运行初始目标保留；每次测量必须绑定数据集版本、流量或负载模型、环境和计算方式。安全关键指标是硬门禁，其他指标若调整必须留下决策记录。

替代方案：暂不写数值。这样能避免虚假精确，但会导致后续各方以不同标准定义“可用”，因此保留目标，同时禁止脱离测量口径解读。

### 6. 后续采用能力 change，不采用一个总实施 change

建议的后续 change 顺序为：

1. `establish-platform-foundation`
2. `add-conversation-run-runtime`
3. `add-knowledge-lifecycle`
4. `add-grounded-knowledge-retrieval`
5. `establish-tool-gateway`
6. `add-api-error-diagnostic-tools`
7. `orchestrate-support-agent-workflow`
8. `add-ticket-management`
9. `add-human-handoff`
10. `add-approval-action-workflow`
11. `establish-security-observability`
12. `establish-evaluation-release-gates`

其中安全、审计和评测需求从首个运行时 change 起就作为横切要求应用，专门的 change 用于形成完整平台能力，而不是推迟所有相关工作。

### 7. 单人建设采用职责矩阵与证据化评审

| 职责 | 当前负责人 | 必需产出或证据 |
| --- | --- | --- |
| 产品与客服业务 | 项目作者 | 范围、场景目录、SOP、验收结论 |
| Agent 与后端工程 | 项目作者 | 架构决策、契约、实现及技术验证 |
| 前端体验 | 项目作者 | 关键流程、状态和可访问性验证 |
| 测试与质量 | 项目作者 | 固定评测集、自动化测试、缺陷记录 |
| 平台与运维 | 项目作者 | 环境、部署、监控、备份和 Runbook |
| 安全评审 | 项目作者；企业试运行前引入目标企业负责人 | 威胁分析、越权测试、审批绕过测试、敏感数据检查 |

单人建设阶段允许同一自然人承担多个工程职责，但每项门禁必须留下独立可复核证据，不得仅以主观确认标记完成。

### 8. 统一核心领域术语

| 术语 | 基线含义 |
| --- | --- |
| 会话（Conversation） | 用户围绕一个或多个连续问题进行的持久对话容器 |
| 消息（Message） | 会话内由用户、人工或系统产生的单条可审计内容 |
| Agent Run | 一条用户消息触发的一次可追踪、可恢复的 Agent 执行 |
| Agent Step | Run 内一个确定性节点或模型节点的结构化执行记录 |
| 工具（Tool） | Agent 通过受控网关访问的有版本业务能力，不等同于底层 API |
| 工具执行（Tool Execution） | 一次经过授权、校验并记录结果的具体工具调用 |
| 知识证据 | 已发布、权限允许、处于有效期内并可定位版本与章节的知识内容 |
| 业务证据 | 由受控工具在记录的查询时间取得并经过脱敏的实时或准实时结果 |
| 引用（Citation） | 将回答中的事实映射到知识文档版本、章节或业务查询来源的可追溯标识 |
| 诊断（Diagnosis） | 基于已取得证据形成的结构化根因、置信度、已确认项和未知项 |
| 工单（Ticket） | 承接未解决问题、人工协作、状态流转和 SLA 的业务记录 |
| 故障事件（Incident） | 影响一个或多个客户或服务组件的已知运行异常 |
| 升级（Escalation） | 自动处理停止并将标准上下文包移交给人工或更高支持层级的过程 |
| 人工接管（Handoff） | 人工成为当前会话或工单的主要处理者，Agent 停止自主回复或操作 |
| 审批（Approval） | 对冻结后的敏感操作和参数作出批准、拒绝或修改后重审的人工决定 |
| 解决（Resolved） | 已提供并验证解决方案，但尚可等待用户确认或重新打开的工单状态 |
| 关闭（Closed） | 用户确认或依据策略超时后结束处理的终态 |
| 风险等级 | R0 至 R4 的服务端操作风险分类，用于决定授权、审批和复核策略 |
| 幂等键 | 保证同一逻辑写操作重复提交不会产生重复业务副作用的稳定标识 |
| 追踪 ID | 贯穿 API、Run、工具、工单和外部依赖日志的关联标识 |

## Risks / Trade-offs

- [基线过于抽象，无法指导实现] → 所有 requirement 使用可观察 scenario，并要求后续 change 明确引用适用基线。
- [基线过细导致频繁修改] → 只固化产品不变量、阶段边界和验收原则；供应商、库版本和物理目录留给后续设计。
- [初始指标缺少真实数据支撑] → 将其标记为试运行目标，测量结果绑定数据集与环境，允许通过评审版本化调整非安全指标。
- [P0 演示范围削弱企业安全边界] → 即使使用 Mock 和固定角色，也保留可信身份上下文、租户语义、工具服务端授权和禁止高风险直执等不变量。
- [四个 capability 存在内容交叉] → 范围规格回答“服务谁、做什么”，风险规格回答“什么条件下允许”，场景规格回答“具体问题怎样处理”，发布规格回答“何时可以发布”。
- [后续团队把 tasks 当成应用实现清单] → 本 change 的 tasks 只覆盖基线资料收集、评审、映射和批准；任何应用实现必须建立独立 change。

## Migration Plan

1. 创建并验证本 change 的四份 capability 规格。
2. 由产品、客服/技术支持、安全和工程负责人评审未决问题及指标口径。
3. 补齐不少于 20 个真实场景和首批人工 SOP，将其关联到 `support-scenario-baseline`。
4. 批准 P0/P1 边界、风险矩阵和发布门禁。
5. 归档本 change，将 delta specs 同步为项目主规格。
6. 依据设计中的依赖顺序分别创建后续能力 change。

回滚不涉及运行系统。若基线未获批准，可以保持 change 未归档、修订对应规格，或废弃该 change；不得通过删除审计历史掩盖已经发生的范围决策。
